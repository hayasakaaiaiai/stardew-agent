## 2. 两处产品修复

### 2.1 跨保存结果会漏报用量

复现：模型请求已经发出，但保存用量报告先清零。模型稍后返回 **123 输入、45 缓存、67 输出 token**，旧实现更新的是已被报告替换掉的对象；当前用量全为 0。跨报告返回的失败也丢失，失败数是 0 而不是 1。

修复 `src/services/model/gateway.ts`：调用次数仍在发出时记录；返回的 token 和失败次数记进返回时的当前统计窗口。有迟到用量、没有新调用的级别也显示，避免再次被 `calls > 0` 过滤掉。回归跨两个保存报告后才返回的请求，所有 token 恰好出现一次，后续报告不重复；迟到失败保留且释放并发槽。

因此日志可能出现“后台 0 次 输入 123（缓存 45）输出 67”：本窗口没有新发起后台请求，但收到了之前请求的用量。调用次数和实际 token 分别按发起和收到结果的窗口统计，跨窗口相加不丢、不重复；它不是按游戏日追溯的账单。

### 2.2 同一次读档重连会重复发起后台场景

复现：一次整点已经完成调用，WebSocket 断线后用原 `loadNonce` 重连并重发原包，旧实现调用数 **1 → 2**。做满 6 次后断线重连，第 7 对 NPC 也会调用，**6 → 7**。每人当天一次的限制同样放在连接对象里，重连就丢了。

修复 `src/bridge/server.ts`：后台次数、已参加的人和最后整点以 `GameSave` 为键存入弱映射。同一次读档重连仍使用原预算；新 nonce 的新读档及新一天有新预算。异步取资料后再次核对读档和日期，过时的请求不继续发出。

回归结果：重连重发后仍只有 **1 次**，下一整点同一批人也不能再参加；做满之后仍只有 **6 次**，新读档才允许重放当天。跨保存才返回的旧日结果没有进入次日，次日仍能正常生成、写入及召回新的场景。

这里保留的是当前后端进程中的同次读档预算；没有增加预算的磁盘持久化。后端进程重启后的预算重建仍沿用现有内存实现，未写入当天日志的后台结果按设计丢弃，不能将本轮重连检查扩大成跨进程预算保证。
