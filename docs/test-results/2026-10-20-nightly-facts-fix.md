## 原因与改法

初版 `3f70b27` 只校验 JSON 形状，允许模型自由改写事实。12:38 真机测试中，NPC 说自己想去墓地，被改成“他说要往墓地走走”，并写进次日上下文；完整失败记录保留在 [原报告](2026-10-20-nightly-windows.md)。

仅增强提示词不够：说话人标记和事实规则能改善输出，但重复测试仍出现“店门口见面”和“刚认识”这类没有依据的补充。因此最终增加代码约束：

1. 为原始台词生成 `t1` 等编号，明确标注 NPC/玩家；用 JSON 引号隔离多行台词和伪造标签。只排除固定开场提示，玩家括号内的真实否定与拒绝仍保留，并有离线回归覆盖。
2. 模型每晚只挑 1–2 条重要记忆，返回它们的原话编号；每条建议 1–2 个编号，最多接纳 3 个有效编号，以保留邀请、答复和确认。
3. 代码核对编号，按原始日志确定说话人和先后顺序，组合完整原话。模型附带的 `text` 或 `speaker` 不参与生成记忆。
4. 错误编号或缺少来源的改写会重试一次，仍失败就保留原状；不会静默丢掉坏条目后退役当天笔记。
5. 印象、计划增加关系、未接受邀请及否定约束；继续使用 `low`，正常每晚每位 NPC 一次模型调用。

记忆内核、数据库表和协议均未修改。代价是引用原话的记忆可能比原来的 80 字改写更长，原有召回字符预算继续控制上下文长度。
