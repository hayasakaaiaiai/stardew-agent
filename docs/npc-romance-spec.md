# 恋爱功能 spec：双向约会、共同回忆、角色差异

> 2026-11-09。用户接受优先实现这三项，沿用本会话“先写 spec、按顺序自主实现、游戏内统一验收”的工作方式。本轮从已推送生活功能 `d7b11a3` 建立 `codex/npc-romance`，工作目录 `/Users/a11/Documents/ChatGPT/stardew-agent-romance`。实现期间不改变正在 Windows 测试的生活功能分支，不自动推送或合并。

## 1. 本轮范围

1. **双向约会**：原版恋人菜单共同选地点、今天／明天、出发时刻及相处方式；玩家发起或 NPC 见面回邀；实际出发、到达、有效相处、完成／取消；提前改期。
2. **共同回忆**：完成后选择记住地点、天气或相伴时光；以后回看、以这次真实记录为依据重访；首条真实完成单独保留，不能编造旧档交往起点。
3. **角色差异**：原版 12 位可恋爱角色全部有两种地点建议、相处偏好与原创邀请／收尾。后台对话继续使用各自既有角色卡，不把同一套台词改名复制。

恋爱仅认原版 `dating`、`engaged`、`married`。8 心朋友与 `roommate` 不走恋爱语义；不自动变更恋爱、订婚、婚姻状态，也不假定多人交往就是排他关系。订婚不提前写为同居，分手后停止未完成恋爱安排，旧经历只作为过去保留。关系公开、独立纪念日奖励、情侣矛盾剧情属于后续建议，本轮不将其写成已实现。

## 3. 玩家流程

原版台词结束后，符合关系的 NPC 出现“我们的约会与回忆”。对方用自己的语气提出两个地点，玩家选定地点，再选今天／明天、10:00／14:00／17:00、安静相伴／留时间聊天，最后明确确认。过去的时刻不能选。退出菜单不创建计划，普通聊天里的随口答应不创建约会。

双方见面时也可收到 NPC 的原版邀请，仍由玩家选择并确认。回邀须有持久冷却，不得每次交谈弹出；拒绝／稍后没有感情惩罚。已有待进行计划时不另开一份。

在约定时刻至其后 60 游戏分钟内，玩家走到 NPC 身边选择出发。NPC 从真实所在位置跟随玩家，只有双方到达计划地图且近距、正常走时才累计有效相处。完整观察到 30 游戏分钟后，玩家结束即完成；路途中、菜单暂停、远离、剧情、时钟跳跃均不计时。现有 90 分钟／夜间退出和原版日程恢复沿用生活活动规则。

晚到过期、提前取消、未达到条件就结束均不伪造完成，也不新增失约惩罚。计划可在未出发时改为今天／明天的合法时段。已出发不在途中重写目的地；需要先结束再另约。婚后也可以出发，科罗布斯室友保持既有家庭陪伴。

约会完成后，原版菜单让玩家选“那里的风景／当时的天气／一起留出的时间”。保存的是明确选择及真实日期、地点、天气、有效分钟，不虚构拍照、演奏或未发生的谈话内容。选择可以稍后补，完成本身不会因为没选而丢失。

回忆入口展示首次和近期真实约会；选“再去一次”创建一份引用旧完成事件的新计划，必须重新实际完成才写成重访。回看不重复加好感或生产同一记忆。

## 4. 角色数据

唯一配置在 `data/romance/profiles.json`，TypeScript 与 Mod 共用；Mod 构建把该文件复制到 `assets/romance-profiles.json`。每人字段：

```text
id, name, opening, invitation, closing,
venues: [{map, label}, {map, label}], focus: quiet|talk, references
```

ID 为 12 人既有小写名单；地图为 `Forest`、`Beach`、`Town`、`Mountain`，恰好两个不同建议。相处文案基于既有性格／喜好／日程，全部原创，来源逐条记于 `docs/npc-romance-content.md`。这些是新玩法安排，不冒充原版剧情。世界天气由真实 Mod 读取，不能把偏爱雨天写成当下已经下雨。

## 5. 事件与存档

复用 `life.sync` 的持久日志、全局 `life-N` serial、32 条分批、ACK 与最终 ready。新增 `romanceProtocol:1` 能力握手；旧后端不能接受恋爱事件时明确要求同步升级。已含恋爱日志的存档不得把不兼容批次发送后假装已同步。

`dateId` 为 `date-<创建 planned 事件的 serial>`，禁止在同一分支重用；例如 `life-42` 创建 `date-42`。所有事件含 `id,npc,day,kind,dateId`，额外字段如下：

| kind | 字段与条件 |
|---|---|
| `romance.planned` | `venue,dateDay,time,preparation,relation,initiator`；可有 `sourceId` 指本 NPC 旧的完成事件；当天／次日，固定时刻，原版恋爱关系 |
| `romance.rescheduled` | 同计划字段，不增加 `sourceId`，保留原来的重访来源；仅尚未出发计划可改 |
| `romance.started` | `relation,venue,time`；time 为真实出发时刻，venue 是目的地，只表示出发不表示到场 |
| `romance.completed` | `relation,venue,weather,minutes,friendship`；真实计划地图至少 30 分钟，weather 为 sunny/rain/storm/snow/windy；friendship 记录实际原版增量 |
| `romance.cancelled` | `reason` 为 player/expired/relationship/interrupted；关系失效可结束旧计划，不携带虚假现关系 |
| `romance.remembered` | `sourceId` 指本次 completed 事件，`detail` 为 place/weather/company；同次只选择一次 |

原生持久状态放入现有 LifeSave 的新增字段，旧档缺省为空。计划、回忆、邀请冷却随游戏保存回滚，不用系统日期冒充游戏日期。

后端将恋爱投影放在同一记忆事务的 `log.romanceState`，读当前 overlay 或当前提交祖先，沿用 `log.lifeState` 已验证的隔离方式。**绝不写 NPC 整体 state**，避免遮挡晚到的夜间印象和计划。混合批次所有事件先完整校验，再一次原子记录；生活与恋爱各自高水位、共同全局 serial 顺序。记录带真实源日，不重复加好感或重新控制 NPC。

近期完成档案最多 24 条，首次完成独立保留；原生回忆菜单与后端来源范围一致。所有恋爱记忆私密，不能进入生活好友分享的公开 source。关系失效后当前约会提示被移除，旧记忆标明过往；仅仅掉心不等同分手。

## 6. 原生动作边界

- 所有菜单回调复核 loadNonce、游戏日、真实关系、NPC 距离和当前阶段；模型输出不能直接改日程或建立恋爱。
- 新约会依赖生活同步完成，已开始约会断线仍能原版结束；NPC 必须释放控制、恢复原日程，旧回程不能跨日／跨存档执行。
- 使用 `romantic_date` 内部活动。它只有恋爱完成／取消事件，不另发一份普通活动完成，避免双份好感和共同记忆。
- 实际出发与普通约定／生活活动共用当天启动额度；完成好感共用已有原版日上限；配偶沿用原有活动好感规则，不另发奖励。
- 新开关 `Romance` 默认开启；关闭后允许已有活动退出、查看过去记录，不能开启新计划。
- 生活日志达到现有上限时保留旧记录并暂停新动作，不删除历史来挤空间。

## 7. 验收与成本

自动覆盖：12 角色配置和来源一致、非恋人／室友拒绝、错误日期时刻／地点、混合批次全局顺序、阶段／dateId／sourceId 校验、改期、完成前回忆拒绝、重复与重访、关系改变、旧 nonce、断线重放、保存回滚／分叉、晚到夜间印象、好感预算、旧生活事件兼容。纯 C# 覆盖出发窗口、指定地图计时、菜单生命周期与来源保留。

prompt 只附当前 NPC 必要计划／近期回忆摘要，角色差异沿用既有卡；完整配置和日记不常驻 prompt。实现前后用仓库外 `gpt-tokenizer@3.4.0` 的 o200k 编码测量候选展开／紧凑写法及实际生产函数。分词是成本近似，不当作模型效果或收费计数。

R0–R3 已完成；R4 离线验证与交付文档已完成，游戏菜单、原生跟随、约会节奏和人物感受由用户按 [全量清单](npc-romance-game-checklist.md) 在 Windows 验收。本轮未运行游戏。精确命令、结果与失败修复记录见 [验证报告](test-results/2026-11-09-npc-romance.md)。

## 8. 实现收口与设计取舍

- 12 人共用 `data/romance/profiles.json`，后端与 Mod 实际加载同一文件；原版角色卡不扩写。莉亚提供森林／海滩，所有角色的两个建议均在 [内容依据](npc-romance-content.md) 中说明。
- 邀请在原版台词结束后的碰面菜单出现。每个 NPC 至少间隔 3 个游戏日，全局每天最多一次；打开邀请即记录冷却，拒绝不扣好感。不额外添加自动寻路找玩家的邀请控制器。
- “安静相伴／留时间聊聊”影响确认内容及聊天时的当前安排摘要，角色偏好改变默认选项顺序；不自动生成一段谈话、不要求送礼，也没有新增收费模型调用。出发后的摘要同样保留此选择。
- 地点判定为整张目标地图近距相处，不作某一风景点坐标判定。因此 Mountain 统一称“山间”，不把矿洞路口相处写成湖边。普通旅行跟随仍复用已有控制器。
- 原生回看菜单展示首次和最近 3 次，去重后最多 4 项；来源校验保留首次和最近 24 次。待选记忆提供最新未选择项，菜单可补选展示的旧回忆。保留范围之外的中间历史不会成为新重访来源。
- 当前关系失效时，即使只剩从未完成的旧计划，也明确它属于过去；已过日的安排不继续执行、不推断失约。完成后的旧日期不会被写成刚刚发生，也不是交往纪念日。
- `romantic_date` 与普通活动共用控制、日启动和好感额度，但仅生产恋爱完成／取消事件，不能作为生活好友分享的来源。日志写入失败时回退好感与计划，释放现有 NPC 控制。
- 恋爱投影写入独立日志命名空间，晚到夜间印象与隔日保存、后端重启、未保存回滚／分叉都有组合回归。全局 serial 由原生持久日志产生；后端检查每个混合批次严格递增，各领域的保留收据核对重放，不新增一个跨领域数据库表。
- 旧后端不支持恋爱协议时，无恋爱历史的旧生活存档仍可使用；带恋爱日志的存档要求同时升级后端和 Mod，禁止静默跳过该历史。关闭 Romance 不删除历史，已开始的活动仍可退出。

实际分词固定 34 张角色卡中的莉亚，恋爱关系、空检索与空对话历史的基线为 **1897 o200k token**；12 个生产场景的摘要增量为 **0–125 token**。把全体 12 人配置额外常驻则再加 **1757 token**，正式实现未采用。详细输入、当前函数 SHA256 与每例数字见 [结果 JSON](test-results/2026-11-09-romance-prompt.json)。该对照只衡量输入成本，不表示自由模型行为已验证。
