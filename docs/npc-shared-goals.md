> 2026-11-09，设计草案，等待用户确认后实现。功能分支 `codex/npc-shared-goals`，基线 `main / 789b911`。本文没有代表新功能已实现或游戏内验收通过。

## 1. 已确认的范围

用户希望同时发展可完成的玩法、人物状态与故事、陪伴活动，排除 H 线；已同意从“莉亚一人、一条三阶段故事”开始开发。

- 一次交齐并消耗 3 块浮木，不限期。
- 反馈为感谢信、共同记忆和后续态度变化。
- 同行沿用现有好感规则，不再增加物品奖励。

本轮先完成接口核查、提示词分词和设计。按 `AGENTS.md`，正式实现前仍需确认本文，尤其是 §2 的建议细节和 §7 的已有文件接入例外。

## 2. 建议采用的细节（待本文整体确认）

| 项目 | 建议 |
|---|---|
| 开始条件 | 莉亚 8 心以上，朋友、恋爱或订婚；非配偶、室友、疏远状态；单人；功能开关开启。8 心选择也与资料中的浮木话题对应 |
| 入口 | 原版台词结束后的原版问题框增加“浮木的事”。首次看到入口不等于接取；菜单里明确选择“我来帮忙”才接取 |
| 触发频率 | 每条存档分支只做一回；未接取可以以后再看，不自动弹窗催促 |
| 交付 | 专用选项“交付 3 块浮木”；不足时提示缺少材料；一次跨背包堆叠扣足 3 块，不改变普通送礼次数 |
| 第二阶段 | 交付后可选择“现在去森林河边”，或“改天再去”。首版只提供当天立即出发，不增加任意日期约定解析 |
| 可出发时段 | 非节日、非剧情，09:00–17:00，双方无冲突约定，日程可用；遵守当天约定上限与既有行动开关。拒绝原因在菜单说明 |
| 同行完成 | 本次故事约定实际碰面，在森林同图、距离不超过 8 格累计同行至少 30 游戏分钟，随后玩家选择结束或正常到点结束 |

| 提前结束 | 不足 30 分钟则回到“材料已交、待同行”，以后可再约；不再收材料。只有明确结束整条目标才关闭故事 |
| 关系变化 | 接取后心数下降或结婚时保留进度，暂停不满足条件的同行；提供“先到这里”结束目标。已交材料不返还，保留交付感谢，绝不写成同行完成 |
| 结局 | 完整完成，或玩家明确选择结束。未交材料直接结束不寄信；已交材料的提前结局只感谢材料 |
| 态度 | 接取后期待、交付后感谢、同行时放松、完成后觉得玩家可靠；关闭目标不贴失约标签。完成或关闭后的专门提示保留 3 个游戏日，此后仅按现有记忆召回 |
| 好感 | 材料交付、结局和寄信不另加点；赴约沿用现有计算和每日上限。重约占正常次数，不绕过限额 |
| 感谢信 | 依据结局生成原创固定短笺，无赠品，不依赖夜间模型。次晨起进入待寄队列，遵守 §5 的每日一封规则 |
| 进度查看 | 从“浮木的事”查看。首版不接原版任务栏；目前代码没有任务栏集成，后续可独立扩展 |
| 首版内容 | 备料、森林散步、感谢；不宣称木雕已完成，也不触发或替代原版艺术展、赠送雕像和 14 心事件 |

开始资格只限制首次接取。已经接取的目标，即使后来跌破 8 心或结婚，仍能从“浮木的事”查看并结束；剧情／疏远阻止当面对话时延后显示，保留进度，不能因为重新套用开始资格而锁住退出入口。

上述设计把轻量情绪嵌入一个可完成的目标。通用信任数值、其他 NPC 的目标、群体故事与家庭活动留给后续版本。

## 3. 玩家流程与状态

原版菜单负责接取、交付、出发和结束。自由对话可以讨论进度，不能通过“我交过了”等文字直接推进目标、扣物或发奖。模型正常输出的三个选项也不能绕过正式菜单改变目标。

| 状态 | 已发生的事实 | 可执行动作 |
|---|---|---|
| `offered` | 尚未接取 | 接取、以后再说 |
| `collecting` | 明确接取，未交材料 | 查看要求、交付、结束目标 |
| `ready` | 已实际扣除并交付 3 块浮木 | 现在去、改天再去、结束目标 |
| `scheduled` | 本次故事邀约已建立，尚未碰面 | 等待碰面、取消本次同行 |
| `walking` | 正在本次故事同行 | 继续、提前回去、达到条件后结束 |
| `completed` | 本次同行达到条件并结束 | 查看结果；之后按真实事实聊天 |
| `closed` | 玩家明确结束整条目标 | 查看结果；保留实际交付事实，不能再次接取刷奖励 |

`scheduled` 或 `walking` 的一次尝试失败、未碰面、提前结束、保存前仍未结束，均不自动关闭目标：回到 `ready`，不重复扣料。保存时若已满足同行条件，正常结束该尝试并完成目标；否则只保留材料阶段。只有合法的同场同行区间能累计时间，菜单暂停没有时间增量。

每个目标有稳定 `goalId`，每次重约另有 `attemptId`，每次目标转换增加 `revision`。普通森林约会不能完成本故事；旧尝试的取消或完成报文不能影响新尝试。`goalId`、`attemptId` 必须随约定构建、取消和结束传递，不能只凭 NPC、日期和地点猜关联。

首版菜单预约固定“现在去森林河边”，避开新增一套自然语言接取与时间解析；已有自由对话约定仍照现有规则处理，发生冲突时拒绝新的故事出发，不覆盖旧约定。

## 4. 物品、存档与事实来源

### 4.1 Mod 是物品和目标进度的来源

Mod 新增目标模块，维护版本化快照：`schema`、`goalId`、`revision`、阶段、接受与交付日期、当前尝试、实际同行统计、结局、待确认转换及待寄信。

交付回调执行时再次检查本次读档身份、目标阶段、背包数量、后台连接和可靠队列容量；条件失败不扣材料。成功时在游戏主线程的一段同步操作内完成扣物、阶段转换和记录待发送事件。异常必须撤销该段内的扣物与状态更新，不把“部分成功”显示成完成。

物品以原版内部身份核对，不能按中文显示名匹配。实现前从合法安装的 `Game1.objectData` / `ItemRegistry` 核对浮木的物品 ID；找不到或非唯一时关闭交付，并给出可诊断原因。本轮未验证具体 ID，不把猜测写为确定常量。

任务交付不发 `gift.given`，不计入 `GiftsToday` / `GiftsThisWeek`，不伪造玩家送礼。普通送给莉亚浮木仍是普通礼物，不自动抵任务材料。

### 4.2 后端只镜像实际转换

新增目标消息，建议协议从 3 升到 4，旧组合明确提示需同时升级 Mod 与后端。所有消息沿用 `lineageId / loadNonce / seq`，增加目标与尝试关联、revision 和事实字段。具体字段编码在实现时按现有协议形式定义，不新增模型输出字段。

后端沿现有串行队列、身份校验和收据流程，调用 `NpcAgent.record()` 原子追加目标日志和 observation 记忆。状态镜像使用现有 JSON namespace；写入时保留同一 NPC 的其他状态，不覆盖夜间印象或计划。既有夜间整合保留自定义状态字段，但其可读文本不是任务完成依据。

目标菜单的命令必须有代码侧事件记录，不伪造成模型说过的自然语言。每条事实按实际阶段生成：如“农场主交给我 3 块浮木”，或“农场主陪我在森林走了至少 30 分钟”。只写在莉亚的记忆分区，不自动扩散给全镇。

### 4.3 回滚、去重与恢复

- 物品和 Mod 目标快照一起随游戏存档保存；不保存退出时同时回滚，后端依存档提交指针回到同一分支。
- 现有可靠消息队列只在游戏进程内。**必须额外持久保存尚未确认的目标转换**；不能只依赖既有队列重发，否则保存后断联退出会丢交付事实。
- 相同读档下后端重启：普通可靠队列补发；目标 revision 和事件身份防止重复记忆。
- 新读档：先完成原有存档指针对齐，再核对 Mod 目标快照与后端镜像；持久待确认转换按 revision 顺序同步。对可验证的保存后缺口，只补已记录的事实和阶段，不再次执行扣物、好感或投递动作。
- `save.ready` 只代表原存档桥接已就绪。另设绑定当前 `loadNonce` 的目标同步屏障：pending revision 补齐并确认目标同步完成前，交付、出发、结束操作不可用，提示正在同步；不把旧目标镜像放进模型上下文。同步失败保留恢复证据。
- 恢复事件保留原始发生日与来源提交／待确认标记；补回当前事务的记录标明恢复来源，不能伪称当天刚交付，也不修改已经确认的旧提交。
- 无法证明归属的矛盾快照不自动覆盖另一端，暂停本目标的新交付并报告原因；原版玩法继续可用。
- 幂等作用域包含存档谱系及当前可达分支／读档，不用跨分支全局 `goalId + revision` 去重。旧档分叉可以各自继续同一个故事。
- 普通消息 ACK 只确认后端当天事务已记录。只有转换已进入本游戏保存指针引用的已确认提交，并且 Mod 目标快照与该指针共同成功保存，才可清理对应恢复证据；ACK 到保存确认之间继续保留持久待确认记录。
- `SaveSync`、后端收据写入和目标同步必须通过故障窗口测试，不能以静态快照相同代替崩溃恢复验收。

## 5. 感谢信、态度与既有行动

### 感谢信

目前 `GameSave.today()` 每天只挑一封普通来信，`letterFor()` 仅接受前一天的信；直接复用夜间 `letter` 字段可能被过滤或漏掉。因此目标信单独持久排队，使用现有原版信箱与正文保存路径投递。

建议维持所有 Agent 信件每天总计最多一封：有到期的故事信时优先占位；若当天普通信已实际入箱，故事信顺延，不撤回现有信。没有占位的普通候选按现行挑选机制处理。故事信不会因晚一天而过期。`SendLetters=false` 时保持待寄，重新开启后再按限额投递。

每日额度只由 Mod `Letters.cs` 的实际入箱路径裁决，普通信和故事信共用同一入口，持久记录绝对游戏日与投递键；后端发送候选不占额度。后端仅传递／读取投递结果，不另建一套占位权威。

入箱和已读均使用稳定键去重；待寄、已寄、正文与游戏邮件字段一起保存／回滚。相同结局不会重复寄信，读回结局之前的旧档允许在该分支重新产生信。

完整结局的原创草案：“谢谢你送来的浮木，也谢谢你陪我在林子里走走。在树影里慢慢走一阵子，心里很自在。有空再来找我吧。”

仅材料结局的原创草案：“谢谢你留给我的浮木。那些曲曲折折的纹路很有意思，够我琢磨一阵子了。有空再来聊聊吧。”

这两段是本 Mod 的新台词，不是游戏原文；不声称作品已完成。文本经原版字符转义后展示，不携带物品指令。

### 态度与同行

态度由实际阶段映射为短提示，帮助模型保持上下文。它不改角色卡、不替代原版心数，也不建立新的信任分数。结束后专门提示持续 3 游戏日，已发生的记忆仍按原召回策略保留。

实际出发和同行仍受 `NpcMeetings`、`MeetingsGoTogether`、日程、每日约定数及关系限制。关掉功能不能导致“完成”。中途结婚或条件变化时显示暂停原因，玩家可选择材料结局，避免默默卡住。

通过故事 ID 绑定现有赴约结果和好感收据，故事目标不另发一份好感。重约时也不能绕过原有每日上下限。

## 6. Prompt 成本与测量范围

本轮没有调用真实模型，没有新增项目依赖。分词使用临时隔离目录中的 `gpt-tokenizer@3.4.0`、`o200k_base`；npm 元数据显示该版本发布于 2025-11-07，超过两周。该工具仅用于方案成本核对，未写入 package.json 或锁文件。

上一轮同内容草案独立片段为完整叙述 145、精简状态 83 token。本轮按最终菜单流程重写各阶段提示，并实际调用基线 `buildMessages()` 比较消息正文；模型系统规则和角色卡原样保留。目标片段追加到 `MemoryContext.summary`，不能替换已有印象。

固定样例：莉亚、8 心朋友、无已看事件、第一年夏 4 日 14:00、晴、森林、空历史，玩家问“最近怎么样？”。无目标时，空记忆基线 1892 token，带既有印象基线 1909 token。

| 阶段 | 片段本身 | 完整正文增量：空记忆 | 完整正文增量：已有印象 |
|---|---:|---:|---:|
| 未接取 | 68 | +59 | +68 |
| 待交付 | 66 | +57 | +66 |
| 已交付、待同行 | 65 | +56 | +65 |
| 已约、未碰面 | 66 | +57 | +66 |
| 正同行 | 68 | +59 | +68 |
| 完整完成 | 70 | +61 | +70 |
| 仅材料结局 | 70 | +61 | +70 |
| 没有目标片段 | 0 | +0 | +0 |

空记忆的增量更小，是因为原本“暂无可回忆的具体经历”占位行被替换；不能把 +56～61 当成所有实际对话的成本。具体全文与结果见 [测量记录](test-results/2026-11-09-shared-goals-prompt.json)。

首版只在莉亚相关对话带当前阶段；其他 NPC 不带，全局 system 和夜间规则不加常驻段落。规划上不增加模型调用、输出字段或后台轮询；事实转换和感谢信都由代码处理。实际对话输出、推理及后续记忆召回的成本仍可能变化，须在实现后的真实样例中单独报告。

上述数字是 DeepSeek 的分词近似，仅数消息正文，不含 API 封装，不代表真实计费或内容可靠性。首次探针因只给校验器一个 NPC、缺少人际关系名单而失败；补齐 34 人名单后才得出本表，未修改产品校验器。

## 7. 实现文件与仓库边界

现有 `AGENTS.md` 写着其他功能线“只新增 src/ 下的文件”。本功能需要消息分派和桥接接点，单纯新增文件无法接通；**请求在确认本文时一并允许以下最小接入修改**：

| 文件 | 允许的接入改动 |
|---|---|
| `src/bridge/protocol.ts` | 新协议消息与字段校验、版本更新 |
| `src/bridge/server.ts` | 目标消息分派、连接同步 |
| `src/bridge/memory.ts` | 调用新增模块；复用现有串行、收据和记录接口；包装对话上下文；目标约定关联与投递结果传递 |
| `src/agent/meetings.ts`（如类型接入需要） | 仅目标关联和结果字段，保留普通约定规则 |

新逻辑主要放在 `src/agent/goals.ts`、`src/bridge/goals.ts`；不改 `src/agent/npc.ts`、`src/save/`、`src/services/store/`、`src/types.ts` 等记忆内核，也不需要修改 SQLite 表或内核 API。若实现发现需要新内核接口，再明确提出，本文不授权扩大到内核重构。

Mod 新增 `SharedGoals.cs`；接入 `ModEntry.cs` 的原版问题框、`SaveSync.cs` 的持久同步、`Meetings.cs` 与 `Outing.cs` 的尝试关联及实际同行、`Letters.cs` 的去重投递、配置开关。使用现有原版 UI，不绘制新界面。

正式实现以此功能分支推进，不修改 H 线，不合并 main、不推送。用户确认后分两步提交：先接取／交付／存档同步，再同行／态度／来信；两步都通过测试和类型检查后提交并更新本文件与 status。

## 8. 验收计划

### 自己完成的离线与模拟验证

1. 资格、开关、版本和输入校验；不存在的目标、NPC、阶段、revision、attemptId 均不推进。
2. 0/2/3/多堆浮木；数量不足、队列满、旧菜单、重复点击、重复消息不重扣、不丢部分物品。
3. 普通送礼与委托交付互不抵扣；未选择的选项及口头完成声明不改变目标。
4. 模拟 Mod + WebSocket + 临时 SQLite：接取、交付、保存、恢复、回滚、旧档分叉与 NPC 隔离。
5. 强杀后端覆盖记录／收据故障窗口；模拟 Mod 进程退出后丢失内存队列，仍能从存档快照及待确认转换恢复。
6. 普通森林约会、旧 attempt、仅碰面、离图、距离分离、剧情中断、提前结束，均不能误判完成；正常时钟累计 30 分钟后结束才完成。
7. 重约不重扣，冲突不覆盖旧约定，赴约好感只按原机制记一次并受每日限额约束。
8. 已交付后关系变化、关闭功能、选择材料结局；记忆和信件不含不存在的散步。
9. 普通信与故事信竞争、迟到重连、关闭再开启寄信、已读、读旧档分叉，验证每日上限与无重复／丢信。
