# 次日主动提起计划：第一步

> 状态：设计与真实模型预试验已完成，等待确认后实施。分支 `codex/next-day-plans`，基于已推送的 `nightly-consolidation` / `5896878`。2026-10-20。

## 1. 这一步的效果

第二天，玩家第一次点某个 NPC 的“继续聊”时，NPC 先提起昨晚想好的话题。例如双方明确约好做紫色风筝，阿比盖尔开场会问今天的安排；玩家尚未回应矿洞邀请时，她只会再询问，不说已经约好；玩家拒绝时，不再当成共同安排。

推荐先复用现有“继续聊”的原版界面，不自动弹窗打断游戏。主动靠近、改日程、执行制作或移动属于后续独立步骤。这一步只让已有计划参与开场表达，不把它当成执行结果。

## 2. 建议确认的决定

| 项目 | 推荐方案 |
|---|---|
| 触发入口 | 当天第一次“继续聊”的开场，NPC 先提话题 |
| 次数 | 每 NPC 每游戏日仅第一次成功对话有主动计划提示，随后沿用正常对话历史 |
| 计划有效期 | 仅使用昨天整合生成的计划：`state.day + 1 === 当前绝对游戏日`；跳过空计划和过期计划 |
| 依据 | 当前存档分支的计划和按当前好感度可召回的原话；没有昨天的原话证据时正常开场 |
| 未接受、拒绝 | 计划只代表 NPC 意向；以原话核对，未回应只询问，拒绝不算双方约定 |
| 进度 | 不假定夜里已执行计划，不编造材料已齐、制作完成、行动经历或未知天气细节 |
| 记忆 | 开场仍写对话日志；该次开场生成的 `remember` 不写成新事实，避免 NPC 自说被记为玩家新经历 |
| 模型用量 | 复用开场本来就有的请求，不增加固定调用次数；普通轮次和无计划开场增加 0 token |
| 存储 | 复用当天对话日志判断是否已开口；不加数据库表、不改 M1 内核或存档格式 |

这份设计没有授权合并 `main`；已验证夜间分支是否合入，单独由用户确认。

## 3. 存档与异常

- 第一次开场被取消、失败或没有成功写入对话日志，不消耗这次机会。
- 同一读档下后端重启，从当天日志恢复，不能反复把计划当成新开场。
- 不保存退出后重读昨天的存档，今天的对话和开场状态一起回滚，允许再次提起，和游戏进度一致。
- 已保存后进入下一天，按新的 `state.day` 检查，不重复使用旧计划。
- 旧档和 B/C 分支只读取自身祖先与当天事务，不共享全局“说过了”标记。
- 夜间整合还没完成时正常开场，不阻塞对话；当天已有对话后不再补插主动提示。
- 保留角色卡、心数和关系限制；计划不能解锁未达到的心事件或私密话题。

## 4. 提示词预试验

模型 `deepseek-flash`，对话 `thinking=high`。保持同一角色卡、8 心朋友、夏季 4 日上午、原话记忆和开场输入不变，对比普通开场和追加计划段。用 DeepSeek 返回的 `usage.inputTokens` 记录实际计费用量。

| 固定样本 | 普通开场 | 推荐计划段 | 增量 |
|---|---:|---:|---:|
| 双方已答应做紫色风筝 | 1739 | 1881 | +142 |
| 矿洞邀请尚未接受 | 1738 | 1880 | +142 |
| 玩家已拒绝墓地邀请 | 1746 | 1884 | +138 |
| NPC 想问小猫星糖的样子 | 1766 | 1906 | +140 |

这是每位 NPC 当天首次成功开场的增量，不是每轮对话的增量。普通开场每类跑 2 次，推荐规则每类跑 2 次，共 8 次推荐输出，逐项看过说话人、邀约状态和时间表达。

早期仅说“不编造进展”仍出现“昨晚已找齐布料竹条和紫色颜料”；已在推荐规则中明确“没有行动结果”“时间过去不代表执行过”。新样本不再声称备齐材料，未接受邀约均为询问，拒绝样本均由 NPC 自己去，自己的猫话题会主动问起。模型表达仍需在实现后继续做真实游戏验收，不能把预试验当成产品实现完成。

推荐追加段的预试验文字如下；实际日期与计划由代码填充，计划文字用 JSON 引号隔离：

```text
## 这次开场想提起的事
以下是昨天睡前（第 31 天）想好的计划，今天是第 32 天；计划中的“明天”指今天。自然地先提起或询问，别等玩家先问。计划只是你的意向，不证明玩家同意；先核对“你记得的事”的原话，双方明确答应才能说约好了，未答复只询问，已拒绝不再当共同安排。此处没有行动结果，只能提议、核对或追问；时间过去不代表执行过。不要声称材料已经备齐或昨晚做过什么，也不补出物品、风力等未知细节。
- "明天在山上和农场主一起做紫色风筝。"
```

原始证据在本机 `.runtime/morning-plan-probe-2026-10-20T05-24-42-670Z/`（普通开场及早期规则）和 `.runtime/morning-plan-probe-2026-10-20T05-25-44-350Z/`（推荐规则）。没有提交密钥或游戏原文。

## 5. 实现方式

新增 `src/agent/morning.ts`，以 `DialogueMemory` 包装器实现开场条件、日期、证据和记忆过滤。只在开场条件成立时追加提示，不改所有轮次的公共规则。

接入 `src/bridge/memory.ts` 的现有回合租约，以及 `tools/chat/session.ts` 的命令行记忆入口。使用现有 `NpcAgent.context()` 读取该 NPC 的状态和当天日志，复用已有 `AgentMemory` 的好感度召回结果；不改记忆内核接口。Mod 和通信协议不变。

## 6. 实施后的验收

1. 离线覆盖有效/空/过期计划、当天已聊、取消与失败、无原话证据、玩家括号内拒绝、NPC 隔离及开场 `remember` 过滤。
2. 通过真实 WebSocket + 临时 SQLite 验证跨天第一次开场、再次打开、后端恢复、不保存回滚和旧档分叉，不能只测字符串拼接。
3. 真实模型重新跑已接受、未接受、已拒绝和自身话题样本，核对时间与完成进展。
4. 在独立游戏存档副本上自动跑完整流程，确认主动开场实际出现在游戏中，保存后内容仍正确；原档哈希不变。
5. `npm test`、`npm run typecheck`、`npm run build` 和 C# 流程检查通过，记录实际用量和测试报告后提交。
