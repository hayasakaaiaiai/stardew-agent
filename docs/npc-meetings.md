# 约好了就真的去：NPC 按约定赴约

> 状态：用户 2026-10-21 说“推送，然后继续下一步”，沿用“后续有需要决定的地方你自行定夺”，按推荐自行决定（§2）。已实现（§7），等 Windows 验收（§8）。分支 `m2c-meetings`，建在 `m2c-approach` 上，目录 `/Users/a11/Documents/ChatGPT/stardew-agent-gifts`。这是 `status.md` §7 第 11 条路线的第 ② 步，也是 `npc-schedules.md` §9 推迟的“改日程”。

## 1. 为什么做

现在玩家和 NPC 说“明天下午海边见”，NPC 也答应了，第二天开场会提起这件事。但到了下午，NPC 照样走原版日程，根本不去海边。约定只停留在嘴上。

这一步让约定变成真的：夜里 NPC 记下明天几点在哪见，第二天到点自己走过去，在那里等一个半小时。玩家来了，他招呼玩家，聊天时知道“我们约好在这儿见”。玩家没来，他等完离开，记住“我等到三点半，农场主没来”。

走路全部交给原版：在当天的原版日程里插两站，“去约定地点”和“回到原日程那时该在的地方”，跨地图、开门、绕路都由原版的日程寻路处理。以后帮忙种地、陪下矿洞，也会沿用这种“临时改一天日程”的做法。

## 2. 决定

| 问题 | 决定 | 理由 |
|---|---|---|
| 约定从哪来 | 夜间整合多一个字段 `meet`：农场主明确答应明天在某个时段、某个地点见面才写，写时间、地点和定下约定的原话编号；否则 `null` | 实测 §3：10 种对话各 3 次，30/30 全对，包括没答应、被拒绝、没说地点、地点不在列表里、约的是后天 |
| 代码再核对 | 原话编号都要存在，至少一句是玩家说的；引用的原话里要有地点的说法（海边、酒吧……）、时段的说法（下午、三点……）和“明天/明早/明晚”；时间在 8:00–21:00 | 和夜间记忆一样，只认原话里有依据的；对不上就当没有约定 |
| 时段怎么换成时间 | 早上 9:00、上午 10:00、中午 12:00、下午 14:00、傍晚 17:00、晚上 19:00；说了几点就按几点 | 写进规则，模型照做（实测全对） |
| 地点 | 只能从 8 个里选：海滩、镇广场、墓地、山上湖边、森林河边、博物馆、星之果实餐吧、杂货店 | 每个地点用原版 NPC 自己站过的格子（§4.1），寻路一定走得通；家里、农场以后再说 |
| 什么时候到 | 约定时间前到。按原版“到达时间”日程的算法估路上要多久，提前出发，再多留 10 分钟 | 原版日程写的是出发时间 |
| 等多久 | 从约定时间起等 90 分钟，最晚到 22:00，然后回到原日程那时该在的地方 | 原日程那段时间的其他站跳过 |
| 玩家来了 | NPC 已到、玩家在同一张地图 6 格以内：冒开心表情，喊玩家名字，面向玩家，算“来了” | 和主动走过来的招呼一致，0 token |
| 聊天时知道约定 | 当天和他“继续聊”时，`## 当前情况` 多一行：`- 和农场主的约定：今天 14:00 在海滩见面`；在约定地点碰面时再加“，现在就在这里碰面了”。过了 90 分钟不再写 | 20–26 token，只在有约定的那天、那位 NPC |
| 事后记得 | 等完（或当天结束时已过约定时间）Mod 发可靠消息 `meet.ended`，后端按模板记一条：“约好 14:00 在海滩见面，农场主来了。”（重要度 2）或“……我等到 15:30，农场主没来。”（重要度 3），跟当天保存或回滚 | 不调用模型；没到过约定地点的（路不通、被剧情打断）不记 |
| 谁不去 | 配偶、室友（原版有专门的日程）；当天没有原版日程的（节日、被剧情接管、本来就不走动的）；同一个地点两个格子都被占了 | 不改不该改的日程 |
| 一天几个 | 每位 NPC 一个，全部最多 3 个 | 只来自昨天确实约好的 |
| 下雨 | 照去 | 约好了就去；以后看情况再加 |
| 当天又改口 | 这次不管，照去 | 改口要在白天的对话里识别，另做 |
| 配置 | Mod 新开关 `NpcMeetings`，默认开 | 会改 NPC 的日程，要能关掉 |
| 协议 | 新消息 `day.meetings`（和气泡、来信一起发）、`meet.ended`（可靠，回 `ack`）；`talk.open` 可选字段 `atMeeting`；版本不变 | 旧 Mod 不认识就忽略 |

### 4.2 改日程（Mod，`Meetings.cs`）

原版 `NPC.Schedule` 是“出发时间 → 路线”，每条路线早上从上一站的终点算好。所以只能成对地改：

1. `stopAt(t)`：原日程在时间 t 让 NPC 待在哪（出发时间不晚于 t 的最后一站的终点；一站都还没出发就是他现在的位置）。
2. 去：`pathfindToNextScheduleLocation(stopAt(出发), 约定地点)`，出发时间 = 约定时间 − 路上时间 − 10 分钟（路上时间照原版到达时间日程的算法），不早于下一个 10 分钟。
3. 回：`pathfindToNextScheduleLocation(约定地点, stopAt(离开))`，带上那一站原来的朝向、结尾动作和位置台词。
4. 删掉出发到离开之间原有的站，插入这两站。离开之后的站，原本就是从 `stopAt(离开)` 出发算的，路线仍然对得上。
5. 路线算不出来（找不到传送点、两站之间路线为空）就不改，日志记一行。

收到 `day.meetings` 就改（离出发至少还有 10 分钟才改，太晚的跳过）。读档、新的一天时原版会重新生成日程，Mod 重新收到消息再改，所以回滚也对得上。

### 4.3 碰面和事后

- 每半秒检查：已过出发时间，NPC 到了约定格子附近（2 格内）、没在走，就算“到了”（原日程本来就让他在附近的，出发前不算）；玩家在同一张地图 6 格内，就招呼一次，算“来了”。玩家和他“继续聊”时，在约定地点也算“来了”。
- 时间走到离开时间：已经到过约定地点的，发 `meet.ended`。当天结束（保存前）时已过约定时间、到过地点但还没发的，也发出去，离开时间写当时。
- `talk.open` 在 NPC 正处于约定时段、人在约定格子附近时带 `atMeeting: true`。

### 4.4 后端

- `nightly.ts`：规则加 `meet`；解析出错当 `null`，不让整晚失败。代码按 §2 核对原话后，把 `{ time, place }` 存进 NPC 状态，每晚覆盖。
- `meetings.ts`（新）：地点和说法、核对、`meetingFor`（昨晚定的、今天的）、对话里那一行、事后记忆的模板。
- `GameSave.today()` 多返回 `meetings`，服务器发 `day.meetings`；`talk.open` 时读这位 NPC 今天的约定，加那一行；`meet.ended` 像送礼一样写进他当天的日志，跟当天保存或回滚。

## 10. Windows 补测中的来源校验修复（2026-10-22）

上游 194/194、合入原 Windows 修复后的 210/210 都通过，但新增错误模型注入复现三个缺口：畸形地点 `constructor` 等继承属性会抛错；拒绝／未答应的原话也能组成约定；引用下午 14:00 却输出 09:00 会通过。新增回归三项在旧代码上全部失败，证据保留在 `.runtime/meetings-source-guards-red.log`。

改用自有地点键，并保守核对双方意向、明确拒绝／未决定／条件和原话时间；明确的后续取消覆盖较早的答应。中文几点、半点与时段按已有规则换算，不能把“后天”混成“明天”。模糊或矛盾时不生成约定；这是有限中文规则，不宣称理解任意语句。正常 prompt、状态格式、依赖均不变，修复增量 **0 token、0 次模型调用**。原端到端假对话只有“回复 N”，没有真正答应，补成明确答应的夹具，并引用双方原话。

具体时刻优先于同一时段的笼统答复：“明天下午三点博物馆见／好，明天下午见”保留 15:00，不被默认下午 14:00 拒掉；“明天早上见”则属于矛盾。短答“可以啊／我可以／我愿意／行啊／好嘞／嗯嗯”也可表达同意。明确的“还没想好／还没定／可能／不确定”不能靠模型补成确定约定。另以真实 WebSocket 注入 `meet.ended` 的继承属性地点，旧代码误记 3 条，修复后确认但不记录；不改存储内核或接口。
